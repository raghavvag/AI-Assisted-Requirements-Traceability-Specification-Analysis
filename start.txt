1. WHAT THE PRODUCT DOES, IN ONE MINUTE
-------------------------------------------------------------------------------
Business people write requirements in an SRS (Word / PDF). Developers build an
API (OpenAPI spec) and code. Over time the API drifts away from what the SRS
asked for. We call this "specification drift".

The product:
  * reads the SRS (tables, tagged headings, "shall" sentences, and now even
    UML diagrams) and the OpenAPI spec;
  * turns every requirement and every endpoint into a 768-number "meaning
    vector" and compares them (cosine similarity), giving a traceability
    matrix;
  * compares API v1 and v2 to find drift;
  * explains every problem in plain English with an LLM;
  * runs as a GitHub App: on every pull request it posts PASS / WARN / BLOCK
    and can block the merge.

  - httpx -> GitHub REST + GraphQL API (the GitHub App)

    and endpoints
  - jinaai/jina-embeddings-v2-base-code -> Python code (AST code scanning)
  - scikit-learn TF-IDF -> the keyword baseline for the benchmarks
  - OpenAI gpt-4o-mini (primary) / Groq llama-3.3-70b (fallback)

  - OpenAI gpt-4o-mini vision -> reads UML diagrams inside the SRS (opt-in)
  - Tesseract OCR via pytesseract -> optional, offline diagram text
  - python-docx (Word), pdfplumber + pypdfium2 (PDF), Pillow (images)
  - prance + openapi-spec-validator (OpenAPI), PyYAML, pydantic (config)

VECTOR DATABASE
  - Qdrant, run with Docker (see section 3)

DEVOPS
  - Docker Compose (Qdrant only)
  - GitHub Actions: .github/workflows/ci.yml (ruff + pytest + frontend build)
    and compliance.yml (the traceability gate on this repo itself)
  - action.yml: a reusable GitHub Action, so any repo can use the gate with

  - smee.io: a webhook tunnel from GitHub to your laptop
  - pytest (482 tests), ruff (lint)

HOW THE PIECES TALK

3. THE VECTOR DATABASE (QDRANT) AND DOCKER
-------------------------------------------------------------------------------
Which vector DB?  Qdrant (https://qdrant.tech), an open-source vector search
                  engine.
What it stores:   one 768-dim vector per requirement and per endpoint, in the
                  collection "requirements_traceability". Every point has
                  user_id + project_id in its payload, and every search is
                  filtered by them, so users never see each other's data
                  (multi-tenant).
Port:             6338 (HTTP/REST) and 6339 (gRPC). We do NOT use Qdrant's
                  default 6333, on purpose.

IS DOCKER USED?
  YES, but ONLY for Qdrant. docker-compose.yml has one service:
      image qdrant/qdrant:latest, container "traceability_qdrant",
      ports 6338/6339, data kept in the Docker volume "qdrant_data".
  The backend and the frontend are NOT in Docker. You run them directly with
  Python and Node (section 5).

IS QDRANT REQUIRED?
  No. If Qdrant is not running, the backend falls back to in-memory NumPy
  similarity and gives the same results. Run Qdrant for the demo anyway,
  because "vector database" is part of the architecture you present.

COMMANDS (from the project root, Docker Desktop must be running)
  docker compose up -d                       start Qdrant in the background
  docker ps                                  should list traceability_qdrant
  curl http://localhost:6338/readyz          expect: all shards are ready
  start http://localhost:6338/dashboard      Qdrant's web UI: open the
                                             collection and show the vectors
  docker compose stop                        stop it (data is kept)
  docker compose down -v                     stop AND delete all vectors

CHECK FROM THE APP
  http://localhost:8000/api/health  ->  "qdrant": {"status": "green", ...}

5. RUNNING THE PROJECT (EVERY DAY)
-------------------------------------------------------------------------------
Open 4 PowerShell terminals at the project root, in this order:

  TERMINAL 1  Qdrant
      docker compose up -d

  TERMINAL 2  Backend (FastAPI)
      cd backend
      python -m uvicorn app.main:app --reload --host 0.0.0.0 --port 8000
    Wait for this log line:
      "GitHub App configured (app id ...); webhook at /api/github/webhook"
    Check: http://localhost:8000/api/health   (status ok, qdrant green,
           config.github_app_configured = true, openai_key_loaded = true)
    API docs (Swagger): http://localhost:8000/api/docs
    NOTE: --reload does not watch .env. After editing .env, stop (Ctrl+C) and
    start uvicorn again.

  TERMINAL 3  Frontend (React)
      cd frontend
      npm run dev
    Open http://localhost:5173  (localhost, NOT 127.0.0.1)

  TERMINAL 4  Webhook tunnel (only needed for the GitHub bot, section 6)
      npx smee-client -u https://smee.io/<your-channel> -t http://127.0.0.1:8000/api/github/webhook

Optional self-checks (no servers needed):
      python -m pytest -q -m "not slow"         fast tests, about 1.5 min
      python scripts/e2e_system_test.py         full lifecycle, offline, ~1 min
      python scripts/e2e_system_test.py --live-vision --live-llm   real models

6. THE SMEE WEBHOOK TUNNEL (FOR THE GITHUB BOT)
-------------------------------------------------------------------------------
WHY: GitHub must send a "pull request opened" event to the backend, but the
backend runs on your laptop (localhost), and GitHub cannot reach localhost.
smee.io is a free public relay:
  GitHub -> https://smee.io/<channel> -> smee-client (on your laptop)
         -> http://127.0.0.1:8000/api/github/webhook

STEPS
  1. Use the channel that is already set as the GitHub App's Webhook URL
     (GitHub -> Settings -> Developer settings -> GitHub Apps ->
     traceability-bot -> General -> Webhook URL). A new channel from
     https://smee.io -> "Start a new channel" also works, but then you must
     paste it into the App's Webhook URL.
  2. Start the backend first (terminal 2).
  3. Run (terminal 4, keep it open for the whole demo):
       npx smee-client -u https://smee.io/KWd6AiEOwb22QSU -t http://127.0.0.1:8000/api/github/webhook
     IMPORTANT: use 127.0.0.1, NOT localhost. On Windows, Node resolves
     localhost to IPv6 ::1, uvicorn listens on IPv4 only, and every event is
     silently dropped, while GitHub still shows the delivery as "200".
  4. Test it: App settings -> Advanced -> Recent Deliveries -> pick any
     delivery -> Redeliver. smee-client prints "POST ... 202", or "200" for a
     ping, and uvicorn logs the request.
       401 = GITHUB_WEBHOOK_SECRET in backend\.env differs from the App's
             secret.
       503 = the App settings were not loaded; restart uvicorn.
  5. Only ONE smee-client should run. Kill any old one that points at
     "localhost".

If smee-client was down when a PR was opened, smee does NOT replay it. Click
"Redeliver" on that delivery, push an empty commit
(git commit --allow-empty -m "retrigger"), or click "Re-run" on the PR's
check.

10. EXAMPLE GITHUB ISSUES (COPY AND PASTE)
-------------------------------------------------------------------------------
The bot reads the issue that the PR CLOSES. Its acceptance criteria (checkbox
lines, or bullets under an "Acceptance criteria" heading) are checked against
the endpoints the PR adds or modifies.

ISSUE A  (leads to PASS)
  Title: Support discount codes in the cart
  Body:
    Shoppers want to use promotional codes in the cart, not only at the payment provider.

    ## Acceptance criteria
    - [ ] A shopper can apply a promotional discount_code to their shopping cart
    - [ ] The cart response shows the discount applied and the recalculated subtotal
    - [ ] An invalid or expired discount code is rejected with a validation error

ISSUE B  (the PR that "solves" it gets BLOCKED on REQ-04)
  Title: Simplify the refund API
  Body:
    Clients keep generating their own refund identifiers and getting them wrong. Let the server own the reference.

    ## Acceptance criteria
    - [ ] A refund request needs only order_id, refund_amount and reason
    - [ ] The server generates a refund_reference and returns it in the response

ISSUE C  (the PR that "solves" it gets BLOCKED on REQ-09)
  Title: Reduce checkout friction
  Body:
    Checkout abandonment is high on large orders because of the extra verification step.

    ## Acceptance criteria
    - [ ] Checkout completes in a single request
    - [ ] Orders are placed without an extra verification step, whatever their value

ISSUE D  (leads to WARN: the PR delivers only half of the issue)
  Title: Wishlist
  Body:
    Shoppers want to save products for later.

    ## Acceptance criteria
    - [ ] Users can save a product to a wishlist
    - [ ] Users receive an email when the price of a wishlisted product drops below a target price

Point to make: the business asked for something (issue C) that silently
breaks an older requirement (REQ-09). Normal tests pass; our bot blocks it.

11. THE GITHUB FLOW, STEP BY STEP: ISSUE -> BRANCH -> PR -> BOT -> MERGE
-------------------------------------------------------------------------------
Before you start: terminals 2 (backend) and 4 (smee-client) are running
(section 5).

Example: the WARN scenario (Issue D), done live.

STEP 1  Create the issue
  Website: github.com/raghavvag/traceability-demo-store -> Issues -> New issue
  -> paste the title and body of ISSUE D -> Submit. Note its number, e.g. #11.
  Or from the project root with the GitHub CLI:
    gh issue create -R raghavvag/traceability-demo-store -t "Wishlist" -b "Shoppers want to save products for later.`n`n## Acceptance criteria`n- [ ] Users can save a product to a wishlist`n- [ ] Users receive an email when the price of a wishlisted product drops below a target price"

STEP 2  Create a branch from main
    cd D:\traceability-demo-store
    git checkout main
    git pull
    git checkout -b feature/wishlist

STEP 3  Make the change: add an endpoint to openapi.yaml under "paths:"
        (same indentation as the other paths)
      /api/v1/wishlist/items:
        post:
          summary: Save a product to the user's wishlist
          description: Adds a product to the authenticated user's wishlist so it
            can be bought later. Returns the wishlist with product_id and added_at
            for each saved product.
          requestBody:
            required: true
            content:
              application/json:
                schema:
                  type: object
                  required: [product_id]
                  properties:
                    product_id: {type: string, description: Product to save}
          responses:
            '201': {description: Product saved to the wishlist}

STEP 4  Commit and push
    git add openapi.yaml
    git commit -m "feat: wishlist endpoint"
    git push -u origin feature/wishlist

STEP 5  Open the pull request. The body MUST link the issue.
  Website: GitHub shows "Compare & pull request" -> base: main,
  compare: feature/wishlist. Title "feat: wishlist". In the description write:
        Adds a wishlist endpoint.

        Closes #11
  (Closes / Fixes / Resolves #N all work.) Click "Create pull request".
  Or:
    gh pr create -R raghavvag/traceability-demo-store -B main -H feature/wishlist -t "feat: wishlist" -b "Adds a wishlist endpoint.`n`nCloses #11"

STEP 6  Watch the bot (5-20 seconds; the first review after a restart is
        slower while models load)
  * smee-client terminal: "POST http://127.0.0.1:8000/api/github/webhook - 202"
  * uvicorn: "Queued review raghavvag/traceability-demo-store#12", then
             "Reviewed ...#12 @ abc1234: WARN (neutral)"
  * On the PR: the "Requirements Traceability" check goes from "in progress"
    to neutral (grey), titled
      "WARN: the linked issue is only partly delivered (50% covered)"
  * A bot comment appears with "Linked-issue intent: 50% coverage" and lists
    the unmet acceptance criterion (the price-drop email).

STEP 7  React like a developer
  * Fix it: add the missing endpoint (for example
    POST /api/v1/wishlist/price-alerts), then commit and push to the SAME
    branch. Every push triggers a new review, and the SAME comment is edited
    (no spam).
  * Or click "Re-run" on the Checks tab to review the same commit again.

STEP 8  Merge
  PASS (green) and WARN (grey) allow the merge. BLOCK (red) disables
  "Merge pull request" IF branch protection is on: demo repo -> Settings ->
  Branches (or Rules -> Rulesets) -> rule for main -> "Require status checks
  to pass" -> add "Requirements Traceability". The check name appears in that
  list only after the check has run at least once.

STEP 9  Show it in the app
  Website -> any project -> PR Bot -> "Live reviews": the new row, with the
  verdict badge, PR link, check run and the exact comment.

THE SAME FLOW FOR THE OTHER VERDICTS
  PASS   Issue A + a PR that ADDS an optional field or endpoint
         (existing PR #4 adds POST /api/v1/cart/discount)
  BLOCK  Issue B + a PR whose refund endpoint drops transaction_id
         (existing PR #5) -> "BLOCK: 1 requirement regressed", REQ-04
  BLOCK  Issue C + a PR whose checkout drops two_fa_token and the 2FA
         sentence (existing PR #6) -> REQ-09
  BLOCK from CODE only: PR #8 (refund handler, Python) and PR #10 (2FA
         step-up deleted in Python). openapi.yaml is untouched; the AST
         scanner catches it.
  The ready-made branches are in D:\traceability-demo-store (add_endpoint,
  remove_idempotency, drop_2fa_requirement, ...). To recreate them:

12. WHAT TO LOOK FOR ON GITHUB (CHECKLIST)
-------------------------------------------------------------------------------
On the PR page:
  [ ] Checks: "Requirements Traceability" by traceability-bot
        success = PASS, neutral = WARN, failure = BLOCK
  [ ] Check title, e.g. "BLOCK: 1 requirement regressed"
  [ ] Check details (click "Details"): a summary table with the SRS file, the
      number of requirements, base/head commits, linked issues, and
      Requirement | Endpoint | score base -> head | delta | severity
  [ ] ONE bot comment (it starts with "AI Compliance Bot"). After each push it
      is edited, never duplicated.
  [ ] In the comment, for each violation:
        Requirement  `REQ-09`
        Defined in   SRS Figure 2 ... activity diagram ... read by
                     vision:gpt-4o-mini   (only for diagram requirements)
        Endpoint     `POST /api/v1/checkout` (modified)
        v1.0 / v2.0 score and Score Delta (e.g. 0.6166 -> 0.5595, -0.057)
        AI Root Cause Analysis: 1. What changed  2. Why it violates
                                3. Remediation action
  [ ] "Linked-issue intent": the coverage %, and which acceptance criteria are
      unmet
  [ ] Bottom line: "Merge is BLOCKED ..." / "allowed with warnings" /
      "consistent"
  [ ] With branch protection on, the merge button is disabled for BLOCK
On your laptop:
  [ ] smee-client shows the POST, and uvicorn shows "Queued review" and
      "Reviewed ...: VERDICT"
  [ ] Website -> PR Bot -> Live reviews has the new row

Why BLOCK? The rule is deterministic, not the LLM. For each changed or removed
endpoint, the bot re-scores it against its top-3 requirements. If a strong
link (score >= 0.60) drops by 0.05 or more, or a medium link (>= 0.35) drops
by 0.08 or more, the requirement "regressed" and the verdict is BLOCK.
WARN = nothing regressed, but the linked issue is only partly delivered.
